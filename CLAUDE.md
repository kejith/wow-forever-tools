# WoW environment (WoW: Forever)

Working folder for everything around World of Warcraft: Forever: characters, auction house, professions and writs, addons, graphics settings.

**Language:** Answer the user in German. Everything that is versioned is English: code, comments, commit messages, documentation, texts of the app and the scripts (German exists only as a translation in the catalogs, see "Languages").

### CI and releases

Releases are automatic in all three repos: **raise the version, commit, push to `main`**. Nothing else is needed; never create tags or releases by hand unless a workflow failed.

| Workflow | Runs on | Does |
| --- | --- | --- |
| `ci.yml` | every push to `main` and every pull request | runs the tests and builds the package. On `main`: if the version has no tag `v<version>` yet, it creates the tag and starts `release.yml` for it (a tag pushed with the workflow token does not start workflows by itself, hence `gh workflow run release.yml --ref <tag>`). |
| `release.yml` | a tag `v*` (pushed by hand or started by CI) | checks that the tag matches the version, tests and builds again from the tag, publishes the GitHub release |
| `build.yml` (this repo only) | called by the two above | tests on Ubuntu and Windows (`npm test`, `go vet` and `go test ./...` in `sim/` with the DB2 tables of the test folder from the Actions cache, `server/test_*.py`), then the Windows installer: builds `wowtools.exe` into `app/build/bin`, `npm run dist`, starts the built app once in capture mode against `scripts/fixtures/goldperhour` (`--require=connection,goldperhour`) and checks that the bundled wowtools answered. Artifacts: `installer`, `screenshots`. |

- **Addons:** packaged by [BigWigsMods/packager](https://github.com/BigWigsMods/packager) (`.pkgmeta`: no README and no tests in the zip; the zip holds the folder `<Name>/` with a generated `CHANGELOG.md`). `tests/check_package.py` checks the zip. The release has the assets `<Name>-v<version>.zip` and `release.json`.
- **CurseForge and Wago (addons):** the release workflow uploads there as soon as the project id is in the `.toc` (`## X-Curse-Project-ID: <id>`, `## X-Wago-ID: <id>`) and the repository secret is set (`CF_API_TOKEN`, `WAGO_API_TOKEN`; `gh secret set CF_API_TOKEN --repo kejith/<Name>`). Until then the upload is skipped. Creating the projects and choosing a license is a manual step on the sites; the repos have no `LICENSE` file yet. Details are in the README of each addon. CurseForge and Wago host addons only, so the desktop app is published on GitHub.
- **App:** `softprops/action-gh-release` publishes the installer with `SHA256SUMS.txt`; the text above the commit list comes from `.github/release-notes.md`. The installer is not code signed.
- **Action versions in use:** `actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7`, `actions/download-artifact@v8`, `softprops/action-gh-release@v3`, `actions/setup-go@v6`, `actions/cache@v6`, `astral-sh/setup-uv@v10.3.3` (setup-uv has no moving major tag; for the MCP server's tests), `BigWigsMods/packager@v2`.

### Addons from GitHub releases

The app does not bundle the addons. `addonInfo` and `installAddon` take the files from a source:

1. **A local checkout**, if one is set: `addonSources` in `settings.json` (`{ "wowmcp": "<folder>", "goldperhour": "<folder>" }`) or the environment variables `WOWMCP_ADDON_DIR` and `GOLDPERHOUR_ADDON_DIR`. Under Windows for example `\\wsl.localhost\orebound\home\rick\work\GoldPerHour`. This gets a change into the game without a release. The card shows "local folder".
2. **Otherwise the newest release** of `kejith/WoWMCP` or `kejith/GoldPerHour`. The app asks GitHub every 15 minutes at most (anonymous clients get 60 requests per hour), "Check for updates" asks right away. The zip is unpacked in the app's data folder (`%APPDATA%\wowmcp-app\addons\<Name>\<Tag>`, in WSL `~/.config/wowmcp-app/addons`), older downloads are deleted.
3. **Without a network** the release downloaded last applies; the card shows "not checked, as of …" with the reason on hover. Without a network and without a download the app cannot install anything and says so.

"Update available" means: at least one file of the source differs from the installation. If the installed version is higher than the source's (installed from a checkout), the addon counts as current ("newer than the source").

## Languages

Addons, wowtools and app work with an English and a German client and follow the client's language. Other clients get English.

- **Principle (gettext style):** the English text is written where it is used and is the key; German is a catalog; a missing entry falls back to English. Names from the game are never translated: they come in the client's language from the addon export and the DB2 tables.
- **wowtools (`sim/internal/i18n`):** `i18n.T("text {n}", "n", 3)` (name/value pairs), `i18n.Mark("text")` (translated later), `SetLanguage(lang, wow)`, `ClientLocale(wow)`, `ShortDate`. Language: `--lang auto|en|de`, else the environment variable `WOW_TOOLS_LANG`, else `textLocale` from `WTF/Config.wtf` (`deDE` → German, anything else English). Catalog `sim/internal/i18n/locale_de.json`, embedded in the binary (one object per tool; the sections still carry the names of the scripts the texts came from). Placeholders are filled as Python's `str.format` did (`sim/internal/pyfmt`). The package's test walks the Go syntax tree and fails on a text without a German entry, an entry no code uses, a text in two sections or different placeholders.
- **App, main process:** `app/i18n.js` (`t('text {name}', {name})`, `setLanguage`, `clientLocale(wowDir)`, `languageOf(locale)`), catalog `app/locales/de.js`. `addon.js` and `releases.js` use it for their error messages.
- **App, window:** `app/renderer/i18n.js` (`t`, `mark`, `locale()` → `en-US`/`de-DE` for numbers and dates), catalog `app/renderer/locales/de.js`. Static texts in `index.html` carry `data-i18n="English text"` (or `data-i18n-title`, or `data-i18n-help` for the text behind a "?" button); `applyLanguage()` in `renderer/app.js` fills them. Texts that contain HTML (`<code>`, `<b>`) are inserted as they are, everything else goes through `esc()`.
- **App language:** `--lang=en|de` on the command line (captures) wins, then `language` in `settings.json` (`auto`, `en`, `de`; the select box in the sidebar), then the client's `textLocale`, then the language of the operating system. The main process passes `--lang <en|de>` to the bridge, so app and wowtools always agree.
- **`app/i18n.test.js`** (part of `npm test`) scans `t(…)`/`mark(…)` and `data-i18n`, `data-i18n-title`, `data-i18n-help` for texts without a German entry, unused entries, different placeholders or HTML tags, and fails on umlauts in code outside the catalogs.
- **Game texts wowtools parses** exist in both languages: tooltip lines ("Equip:"/"Anlegen:", "Use:"/"Benutzen:", hit and crit percent), the Life Tap text, skill requirements. German regular expressions in `tools/upgrades` and German test data are intended.
- **Tables with text** (`ItemSparse`, `SpellName`) are downloaded and cached per client locale: `scripts/cache/<Table>-<build>-<locale>.csv`, the recipe catalog as `recipes-<build>-<locale>.json`. Names of writs and crate items for both languages are in `scripts/data/item_names.json`.
- **Addons:** texts in `Locales.lua` (English default, a block per `GetLocale()` code). The export has `client.locale`.
- **Adding a language:** a catalog per part and its code in the language lists of `sim/internal/i18n`, `app/i18n.js` and `app/renderer/i18n.js`; for the addons a block in `Locales.lua`.

## Desktop app (`app/`)

Electron app "WoW Forever Tools" (Electron 45, no build step, vanilla JS) that brings addons, wowtools and SavedVariables together. It runs locally and has no server. It writes into the game folder in two places, both inside the addon folders: the requests (`AppRequest.lua`) and the lists for the game (`AppData.lua`, see "Lists in the game"). It uses the network in two places: the bridge downloads game tables and an item icon the first time they are needed (wago.tools, only table names, FileDataIDs and the build number), and the main process asks GitHub for the newest release of the two addons (see "Addons from GitHub releases").

**Start from source:** `cd C:\Coding\wow\app`, then `npm start` (`npm install` only after a fresh clone). Needs Node.js and a built `sim\wowtools.exe` (`cd C:\Coding\wow\sim`, `go build -o wowtools.exe ./cmd/wowtools`; Go for Windows) or `WOWTOOLS_BIN`. If the game is somewhere else, set `WOW_FOREVER_DIR`. Fixed settings come from `%APPDATA%\wowmcp-app\settings.json` (`wowDir`, `wowtoolsPath`, `addonSources`, `language`, `sendToGame`). The file exists only once it is created; the user interface has controls for the language and for `sendToGame` (the switch of the card "Lists in the game"). The data folder kept its name `wowmcp-app` when the app was renamed.

**Installed app:** electron-builder (`build` in `app/package.json`) packs `*.js`, `locales/` and `renderer/` into `app.asar` and puts next to it, under `resources/`, `scripts/data/` (the writ and crate names) and `bin/wowtools.exe`. `main.js` separates the two cases with `app.isPackaged`: `ROOT` is `process.resourcesPath` instead of the repo, the bundled wowtools is tried after `settings.wowtoolsPath` and `WOWTOOLS_BIN`, and downloaded game data goes to `%APPDATA%\wowmcp-app\game-data` (handed to the bridge as `WOW_TOOLS_CACHE`) instead of `scripts/cache`. The folder must not be called `cache`: Chromium keeps its own `Cache` in the same place and Windows ignores case. Nothing is installed or downloaded on the first start (until app 1.11 uv fetched Python, lupa and Pillow then). The icon is `app/build/icon.png`. `app/build/bin/` is not versioned (CI builds wowtools there; for a local `npm run pack` in WSL: `cd sim && go build -o ../app/build/bin/wowtools ./cmd/wowtools`).

**Explanations and tooltips:** A page shows numbers and names; what a number means sits behind a "?" (`help(html)` → `<button class="help" data-help>`). Any element with `data-help` opens the one popover `#pop`: on hover and keyboard focus, a click on a "?" pins it, Escape, scrolling or a click elsewhere closes it. `helpAttr(html)` takes HTML (escape the texts yourself), `hintAttr(text)` plain text and replaces the native `title`, which shows late and cannot be styled. Where the "?" goes: tables that repeat (writ tiers, crate tiers, slot cards, consumable cards) get one "?" at the section heading with a definition list (`terms([[term, text], …], foot)`); a single big table (recipes, shopping list) gets it in the column headers (`th([label, cls, info], …)`); an option gets it next to its label (`<span class="label">`). Do not add explanatory paragraphs below a table.

**Saved view:** The window remembers the page, the character and the options of the pages (`state.writs`, `upgrades`, `recipes`, `consumables`, `rotations`, `prices`) in `localStorage` (`wow-forever-tools:view`) and restores them at the next start; a value whose type does not match the default is ignored. Not in capture mode, so screenshots always show the defaults.

**App ↔ addon:** Addons have no file or network I/O. The app writes requests to `Interface\AddOns\WoWMCP\AppRequest.lua` (`WoWMCP_AppRequest = { id = <unix time>, action = "items"|"sync", full = true? }`). The game reads the file on `/reload`, the addon runs every request once per `id` (3 s after logging in) and writes the result to `WoWMCP_Account.lastRequest`. The app sees that on the next `/reload`. Forever also re-reads the `.toc` on `/reload`: new files and new SavedVariables load without restarting the game (tested in the game on 2026-11-15). Caution: `/reload` first saves with the old code and then loads the new one. After an addon update it therefore takes a second `/reload` until data in the new format is on disk.

**Lists for the game** go the same way in a second file, `Interface\AddOns\WoWMCP\AppData.lua` (`WoWMCP_AppData`), which the app rewrites whenever its results change; see "Lists in the game".

## Lists in the game (`sim/tools/ingame`, `Lists.lua` in the addon repo)

The addon shows the app's results in the game. Addons cannot read files, but the client loads every Lua file of the `.toc` on `/reload`; so the app writes a Lua file into the addon folder, as it does for requests.

- **Flow:** AH scan → `/reload` (the game saves) → the app's watcher fires, the bridge computes all four pages for every character and writes `AppData.lua` → second `/reload` (the game loads it). The file is written in one step and only if its content changed (`hash`), only into an installed WoWMCP whose `.toc` lists `AppData.lua` (1.7 or newer).
- **File:** `WoWMCP_AppData = {version = 1, generated, hash, locale, scanDate, chars = {[first name] = {level, lists, tips, vendor, errors?}}}`. A list is `{key, title, note, sections = {{title, note, rows}}}` with the keys `upgrades` (only for a Warlock, the scale knows no other class), `writs`, `crates`, `recipes`, `consumables`; a row is `{id, name, q (quality), n (amount), info, price (copper), shop (goes to the shopping list; not for an upgrade the account already has, whose `info` names the place), sub (indented: belongs to the row above)}`. `tips[itemID]` = up to 4 tooltip lines, `vendor[itemID]` = the chat line for a recipe a vendor sells. Money inside a text is `{m:<copper>}` and becomes coins in the game; `|` is doubled. `version`, `generated` and `hash` come first, `file_state()` reads them from the head of the file. Texts are in the client's language whatever `--lang` says; `hash` covers everything but the time.
- **Window** (`WoWMCPListFrame`, built when first needed): one tab per list, 16 rows at the default size, mouse wheel and slider. Resizable through the grip at the bottom right (600×400 to 1600×1200, right-click: default size); `layout()` in `Lists.lua` and `ns.history.layout` fit rows, info column, result list and plot to the size, which is saved in `ui.size`. A click on a row searches the auction house for the item (Auctionator's shopping tab if Auctionator is there, otherwise the search box of the Blizzard frame), a modified click goes through `HandleModifiedItemClick` (shift: link into the chat or the search box, ctrl: dressing room). "Search the shopping list" searches all `shop` rows of the tab at once. It opens with the auction house (`/wowmcp ah off` turns that off) and with `/wowmcp show`; Escape closes it.
- **Auctionator shopping lists:** per list one list "WoWMCP: <title>" with the `shop` rows of the logged-in character (`Auctionator.API.v1.CreateShoppingList`, search strings through `ConvertToSearchString`, at most 60, names with `;` or `^` are skipped). Synced 5 s after login and when the auction house closes, never while it is open (Auctionator would start searching), and only if the data changed (`ui.synced` = `hash:character`). Lists of an earlier sync that no longer exist are deleted.
- **Tooltips:** `TooltipDataProcessor.AddTooltipPostCall(Enum.TooltipDataType.Item, …)`, with `OnTooltipSetItem` as fallback, only on `GameTooltip` and `ItemRefTooltip`, light blue lines.
- **Loaded?** The addon notes what it loaded in `WoWMCP_Account.appData`, which the app sees one `/reload` later. So the app also counts the file as loaded if the account SavedVariables are newer than `AppData.lua` (the game saved, so it reloaded, after the file was written).
- **Not verified:** nothing of this has run in the game yet. The addon runs in the Lua simulation of its tests (also against a real `AppData.lua`), where widgets answer unknown methods with nothing; so the layout of the window, the Auctionator calls and the tooltip hook still need a look in the game. Lint with `flavor: forever` reports `GetMoneyString` and `HandleModifiedItemClick` as unknown; both are Lua functions of Forever's FrameXML and are guarded.

## Upgrade rating (`sim/tools/upgrades`)

The principle is Pawn's: a weight per stat, the unit is 1 point of shadow spell power. Two things go beyond a fixed Pawn scale: the weights for hit and crit are derived from the character (`build_scale`), and what is rated is always the whole set (`set_value`, gain = value after the swap minus value before). So hit counts only up to the cap. With `--engine on|auto` the combat engine (see below) replaces this scale: gains are then the simulated DPS change of each swap.

- **Stat keys in Forever:** Hit and crit exist only as a shared rating for melee and spells (`ITEM_MOD_HIT_RATING_SHORT`, `ITEM_MOD_CRIT_RATING_SHORT`; tooltip "Improves your chance to hit by 1.0%", German "Verbessert Eure Trefferchance um 1.0%"). The percent values are in the tooltip, otherwise they are converted (10 and 14 rating per 1 %, `learn_ratings` measures that from the export). `norm_stats` translates everything into `sp`, `stamina`, `intellect`, `spirit`, `mp5`, `hp5`, `armor`, `wand_dps`, `hit`, `crit`. Healing, other schools, spell penetration and melee stats count 0.
- **Profiles** (`PROFILES`): `leveling` (enemies up to +2 levels; spirit 0.25, mana/5s 0.7, wand DPS 0.6) and `dungeon` (bosses +3; 0.05/0.3/0.1). Automatic: `leveling` below level 60. These weights are fixed rules of thumb.
- **Intellect and stamina** are computed from level, stats and talents (only if the export has health and mana, otherwise the fixed values 0.35/0.5 and 0.25/0.25 apply). Pool = mana + health × Life Tap ratio. 1 mana = `mana_share` × (13 × level + spell power) / pool points, 1 health for survival = `survival_share` × (13 × level + spell power) / health. Int = 15 mana + crit per int × crit weight, stamina = 10 health × (Life Tap ratio × value per mana + survival value). `mana_share`/`survival_share` are rules of thumb (`leveling` 0.10/0.05, `dungeon` 0.06/0.02), chosen so that Malgruk at level 46 lands roughly at the old fixed weights. A bigger pool lowers the value of each point; at a low level int and stamina count more because spell power matters less there. The values from the character stats apply at the time of the snapshot, so with the buffs active at that moment.
- **Crit from intellect:** since addon 1.3 from the game (`critFromIntellect`), before that estimated as (spell crit − 1.7 % − crit of the gear) / int. For Malgruk (level 46) the estimate matched on two snapshots with 96 and 149 int: 0.0224 % per int, so about 45 int for 1 %. Life Tap ratio from the spell text ("X health … Y mana"), otherwise 1:1; Improved Life Tap +10 % per rank. Life Tap is in wago.tools' `SpellEffect` by now (ranks 1454, 1455, 11688, 11689; an earlier note here said it was missing).
- **Hit:** miss chance against +0/+1/+2/+3 levels = 4/5/6/17 % (from Forever's character display, `Camelot/PaperDollFrameStats.lua`). Cap = miss − the character's `spellHit` (`GetSpellHitModifier`, without gear; Malgruk has 5 %); no miss remains beyond it (`MIN_MISS` = 0 since engine 0.7.1; Classic keeps 1 %, and until then so did the model). While leveling Malgruk is thus 1 % short of the cap. Every percent up to the cap counts like 1 % damage. Suppression is part of `spellHit`: in Forever it gives 1 % hit per rank to every spell (trait tables; until app 1.9.1 the scale added the Classic 2 % per rank for Affliction spells on top).
- **Crit:** 1 % damage = (13 × level + shadow spell power) / 100 points; 1 % crit = that × 0.5 (crit bonus) × the share of the damage that can crit (25 %, with Pandemic 3/3 85 %).
- **Checked in the game:** with Pandemic the DoTs crit (the player, 2026-11-20). **From the combat log of 2026-11-20:** no miss remains once the hit covers it (no miss in 557 casts and 645 area pulses on enemies up to the character's level; with a 1 % floor the chance of that is below one in 100,000), and Life Tap is what the engine computes: the text's amount moves by 1 health per point of spirit (`lifeTapPerSpirit`), Improved Life Tap gives +10 % mana per rank on top, and spell power changes nothing (with 2/2: 510 mana a cast at the sheet's 120 spirit, 538 with 23 more spirit, 552 with 35 more, each the same at 209 and at 231 spell power; 225 casts). **Not checked:** the miss chance against enemies above the character's level (the log has none).
- **Comparison:** rings and trinkets against the weaker of the two slots, two-handers against main hand + off hand, an off-hand item with a staff equipped against the staff. Special effects (`special_effects`: "Use:" and "Equip:" lines that are not a stat from `stats`) cannot be rated by the scale; such items with less than 5 points of gain are listed under "With a special effect, please look for yourself".
- **Owned gear** (`owned_gear`, `carried`): besides the AH, the candidates are the armor and weapons in the character's own bags and bank (any binding) and the ones on the other characters of the same realm folder that are not bound (`bound` is not set: bind on equip, never worn). They cost 0, carry `source` (`bags`/`bank`), `owner` (another character's first name, else none) and `where` (the text: "in your bank", "in Alt's bags"), are not offered from the AH a second time, and sort in front of everything with a price (in the package and with `--sort price`); `perGold` is none. The item's data comes from the snapshot (addon 1.12 writes `stats`, `tooltip`, `classID`, `subclassID`, `bind` for bag and bank items); a snapshot of an older addon has names only, then the item export fills in by ID — the class fields always, stats and tooltip only when the export's name equals the item's name (a random suffix changes both). What stays without stats is listed in `owned.unknown` (`{id, name, source, owner, where}`; `owned.count` = rated owned candidates) and the CLI and the window say: open the bank once with WoWMCP 1.12 or newer, then `/reload`. The bank is as of the last visit. In the game the package row of an owned item is not a shopping row (`shop` false) and names the place; its tooltip line reads "You own this upgrade for <slot>: …". On 2026-11-20: Siegfried's "Gewand des Fäulnisheilers" in the bank is +4.0 HPS over the Robe of Arugal; seven more of his bank items and three of Malgruk's are known by name only. `USABLE_WEAPONS` is still the warlock's set, so a priest's maces are not offered from either source.
- **Package** (`best_package`): knapsack problem with at most one option per slot group (ring pairs, trinket pairs, main hand + off hand as a combination), without items above the own level. Budget = `--max-price` or the own gold. The list is sorted by points per gold; a smaller budget has its own optimum, which is not always the beginning of this list. The knapsack adds up the gains of the single swaps, and gains do not simply add up (the hit cap, with the engine a mana budget that one item already fills): the chosen purchases are valued again as prefixes, a purchase (a pair counts as one) that adds nothing on top of the ones before it is dropped, and the cost is that of what stays.

## Combat engine (`sim/`, `sim/tools/enginebundle`)

A per-class combat model in Go (module `github.com/kejith/wow-forever-tools/sim`, run inside wowtools; `wowtools engine` takes one bundle on stdin, as the former binary `simforever` did), built after the research of 2026-11-20 (WoWSims for the architecture — MIT, see `sim/THIRD_PARTY.md` before porting code; timhul/ClassicSimForever for the data-driven idea — no license, concepts only). Stage 1 evaluates a priority rotation as a closed-form steady-state cycle; Stage 2 (`method: "montecarlo"`) plays the same rotation cast by cast with real rolls.

- **Split:** the tools (`sim/tools/*`) keep everything that needs SavedVariables or localized tooltips (candidate filtering, slot logic, hit/crit percent from tooltips); the engine is pure compute. One `upgrades.compute()` makes three engine runs (`value_batch`): candidate swaps + per-slot removals, the pair/weapon combos, the package prefixes — each run is one bundle (`run.Input`) and one answer (`run.Output`), errors in the answer.
- **Data:** the engine reads the DB2 CSVs from the shared cache (`scripts/cache` or `WOW_TOOLS_CACHE`; `enginebundle` downloads them through `icons.table` first): SpellClassOptions (which spells belong to the class), SpellEffect (base points, per-level scaling, `EffectBonusCoefficient` — Forever bakes the cast-time coefficient per rank into it, verified on Shadow Bolt), SpellMisc/SpellCastTimes/SpellDuration/SpellPower/SpellLevels/SpellCooldowns, SkillLineAbility (the class's spells, `AcquireMethod`), SpellName (localized labels, plus the `enUS` table for the rank chains), and the trait tables TraitDefinition, TraitDefinitionEffectPoints and CurvePoint (talent values per rank, see "Talents"). Character numbers come from the snapshot sheet (they already include gear and buffs); items enter as canonical stat deltas (`simengine.KEY_MAP`), so intellect and stamina work through `manaPerIntellect`/`critFromIntellect`/`hpPerStamina`.
- **Rank chains** (`catalog.buildChains`): Forever leaves `SkillLineAbility.SupercedesSpell` empty for most class spells (678 of 7853 rows have it), so the ranks of a spell are the class's SkillLineAbility spells with the same English name and the same `SpellClassMask`, plus the explicit links that exist, ordered by `SpellLevels.SpellLevel`. The English name is the key because a translation may name the ranks of one spell differently (deDE: Smite rank 1 "Heilige Pein", ranks 2+ "Göttliche Pein"); `enginebundle` therefore also downloads `SpellName` in `enUS` (`catalog.ReferenceLocale`), without that file the localized names are the key. `AcquireMethod` 3 marks a granted version of a rank (a talent's cast, e.g. the second Renew row 425268–425277): it shares the rank number of the trained rank of its level and is not part of the assumed spellbook. Checked against the spellbook export: all 136 "Rank N" lines of Siegfried and Malgruk match. - **Talents** (`sim/talents`): Forever has one spell per talent, and its `SpellEffect` row holds a single value (often the first rank's, sometimes none). The exact value of every rank is in the trait tables: `TraitDefinition` (talent spell) → `TraitDefinitionEffectPoints` (`OperationType` 0, per effect index a curve) → `CurvePoint` (`Pos_0` = rank, `Pos_1` = value); `catalog.TalentValue` reads them. Without the three tables in the cache the engine falls back to the single value in `SpellEffect` (the rules of the overrides file to their `perRank` × rank) and says so (`coverage.talentValues: "basepoints"`, the app shows a notice). The talent spell's auras are decoded generically: 79 (percent damage per school), 72 (percent mana cost per school), 107/108 (flat/percent spell modifiers with class-mask filter), 134 (regeneration while casting, Meditation), 135/174/175 and 137 (healing, spell power of a stat, percent of a stat: applied to item deltas only). The block describes the target of a damage line and the caster of `SPELL_CAST_SUCCESS`. Damage then has amount, amount before crit and target modifiers, overkill, school, resisted, blocked, absorbed, critical (`1`/`nil`), glancing, crushing, `ST`/`AOE`; a heal has amount, base amount, overhealing, absorbed, critical; an energize amount, over-energize, power type, max power; a miss its type (`MISS`, `RESIST`, `ABSORB`, …). `SWING_DAMAGE_LANDED` repeats `SWING_DAMAGE`. No `ENCOUNTER_START` was seen. A log without advanced logging has not been seen; the script takes the same fields without the block.

Never put lines or names of a real log into fixtures, tests, documentation or commits**; the combatlog tests write their own log with made-up units.

The character's level comes from the WoWMCP snapshot (the log does not have it), so the level difference needs one; against players there is none.
  - *Per spell* (`spells[]`): `casts`, `hits`, `crits`, `ticks`, `tickCrits`, `misses` by type, `missPct` (missed or resisted in full, of the casts), `avgHit`/`avgTick` (the base amount: what a tooltip shows), `model = {hit, tick, hitDiffPct, tickDiffPct}` (the engine's `spells` for the same spell ID), `takenPct` (amount without crit against the base amount: what the enemies' debuffs and armor did), `critMult` (the same for crits, divided by it), `resistedPct`, `tickSec` with the fastest and slowest tenth (per target), `uptimePct` (the debuff on any enemy, of the fight time), `mana` and `energizes` (Life Tap), `healing`/`overheal`, `selfDamage` (Hellfire), `sheetCritPct`, and for a spell the engine calls channeled (`channeled` in its `spells`, with `ticks` and `castSec`) `channel = {casts, ticks (of a whole channel), avgTicks, full, died, cut, clipped, short, missed, lost = {died, cut, short}}`: how its channels ended (`channels()`). `full` ran out; `died` = the target died first; `cut` = the character's next cast came before the channel's end (`clipped` of them are one tick short: the cast came a moment too early); `short` = it stopped with no cast after it (moving, an interrupt, the end of the fight); `missed` = resisted in full, not counted as a channel; `lost` = the ticks missing per kind. A tick is a hit of the spell's name on the channel's target between the cast and the channel's end or the next cast of the same spell; a channel without a target (Hellfire, Rain of Fire) counts the hits that land within 0.3 s as one. A pet's spells are rows of their own (`pet` = its name). `buffs[]` = `{spellId, name, own, uptimePct}`: every buff on the character the log saw start, whoever cast it, with its share of the fight time (they explain why the spell power moves). `hit[]` = casts and misses by the enemy's level above the character with the hit table's number, `fights[]` = `{n, start, seconds, enemies, targets, levelDelta, kills, damage, dps, healing, taken, manaStartPct, manaEndPct, manaLowPct, healthLowPct, spells[], casts[]}`.

- **Buffs and re-optimized evaluations (engine 0.9.0, for the consumables):** the bundle key `buffs` (a stat delta like an item's; `simengine.start(..., buffs=…)`) is applied to the character before anything is rated, so the baseline, the evaluations, the situations and the heal table all include it; only the per-rank spell numbers (`spells`, what the tooltip check compares) stay without it. The answer echoes it (`buffs`). The bundle flag `reoptimize` (`Engine.batch(evals, reoptimize=True)`) makes every evaluation pick the best rotation again for the changed character instead of keeping the baseline's (an evaluation is then exactly the baseline of a run with the same delta as `buffs`). Gear swaps keep the fixed rotation; the consumables need the new one: with the mana of a rune Siegfried's best heal rank changes, and with the fixed rotation the gains of his set added up to half of what the set really gives.
- **Monte-Carlo (M5, since engine 0.2.0; the engine is at 0.10.0):** `--method montecarlo` (UI: Rating "Kampfmodell (Monte-Carlo)") plays the rotation with the player of `sim/engine/play.go` (`RunMC` in `mc.go` draws the dice; the rotation guide runs the same player without dice): real hit/crit/damage rolls per cast, DoTs tick on their schedule and are recast when they fall off, Life Tap on demand, wand when mana runs dry, full spirit regeneration five seconds after the last cast. The baseline carries `mc = {iterations (default 10000), mean, stdDev, p10, p90}` and its value becomes the MC mean; only the `mcTop` (16) biggest closed-form gains are replayed (`results[key].mc = true`), the rest keep the deterministic delta. All runs share the per-iteration seed (common random numbers), so gear differences are not dice differences, and the same seed reproduces the same numbers. DoT ticks apply their crit as an expectation per tick, not as a roll. Health is tracked: Life Tap may take it down to 60 % of the pool, leech and hp5 refill it; the player taps early (health bar full, mana will not last for the rest of the fight) so that no leech is wasted, and a filler that returns health goes before the DoTs when health blocks tapping. A conversion with a duration (Dark Sacrifice) pays out tick by tick, and a damage rotation casts it only if the health projected over the rest of the fight stays above those 60 %; a healer casts it when its mana buys more healing than the health it costs. A cast or channel that the end of the fight cuts off counts for the part that fits (since engine 0.6.0). ## Writs and trade crates (`sim/tools/writs`)

- **Gold on completion:** The writ quest (item → `ItemSparse.StartQuestID`, e.g. 264012 → 94212) pays no gold itself. The game's quest cache (`_forever_\Cache\WDB\<locale>\questcache.wdb`, record = quest ID, size, data; `RewardMoney` at offset 48, reputation from offset 300 as faction and value × 100) has 0 gold and 75/125/200 reputation with the factions 2586 and 2587. The pay is a coin pouch (according to wow.gg; the DB2 has four, 284583–284586) whose content is rolled when it is opened. Until the addon (since 1.5) has measured pouches, estimates per tier apply (`POUCH_ESTIMATE`: Journeyman 33 s, Expert 70 s, Artisan 75 s, after conquestcapped.com, Nov 2026). Measured, the pouch of the own quest counts, otherwise the pouch other writs of the same tier gave. Net = writ + item − pouch, sorted by net per reputation; negative = profit.
- **Trade crates:** A waylaid (empty) crate (248682–248699 and 248702–248713: herbs, ore, textiles, curiosities, fabrics, ingots, parts; Expert and Artisan with earthly and flowering herbs) is filled with exactly one bundle. The spell "Fill Crate" has the amounts as dummy effects in `SpellEffect`; `CRATES` is checked against that, the item IDs of the bundles are only in the guides. The sealed crate (common 248765–248769, uncommon 248770–248774, rare 248775–248779, each Apprentice, Journeyman, Expert, Artisan, Elite) gives Merchant's Favor (currency 3402) at the trade representative, no gold and no reputation. Favor common/uncommon according to urgametips.com and wow.gg: Apprentice 5/10, Journeyman 10/20, Expert 15/30; Artisan 20/40 is extrapolated. Values measured by the addon win. Character level: Apprentice and Journeyman 10, Expert 20, Artisan 35.
- **Calculation:** the empty crate at the AH price (owned 0, without an AH price "incomplete") + the cheapest bundle the AH has in the full amount (own bundles 0). "Per favor" uses the common crate.
- **Unknown:** what the quality of the sealed crate depends on, Elite crates (no waylaid Elite crate in the DB2, content unknown) and what a Merchant's Favor is worth in gold (favor vendor: recipes 15–360, tabard 200, pack kodo 6000).
- The writ list in `tools/writs` is from wow.gg (Nov 2026); add new writs there to `WRITS` and their names in both languages to `scripts/data/item_names.json`.

## Recipe calculation (`sim/tools/recipes`)

- **Catalog** from the DB2 tables (`build_catalog`, stored as `scripts/cache/recipes-<build>-<locale>.json`; raise `CATALOG_VERSION` when the structure changes): `SkillLineAbility` (recipes per skill line; `TrivialSkillLineRankLow` = yellow, `…High` = grey, green from the middle; `MinSkillLineRank` is always 1 in Forever and is useless as the required skill), `SpellReagents`, `SpellEffect` (effect 24 = created item, amount in `EffectBasePointsF`; effect 36 = learn a recipe), `ItemEffect` + `ItemXItemEffect` (recipe items: through a learn effect or, as in Classic, with the recipe spell directly on the item), `ItemSparse` (names, `BuyPrice`/`VendorStackCount`, `SellPrice`, `Bonding`, `RequiredSkillRank` = required skill of the recipe item), `SpellCooldowns` (transmutes; in Forever e.g. Iron to Gold 1 h, Arcanite 47 h). Gathering professions (182, 186, 393, 356) are left out. If the tables cannot be downloaded, `compute` reports that instead of an empty result.
- **Table download** (`icons.table`): a file counts as a table if its first line has an `ID` column (`SkillLineAbility` does not start with it) and is written in one step, because several bridge processes may fetch the same table at once.
- **Learned** comes only from the addon export (`WoWMCP_Char.recipes`). The profession window API delivers data in Forever only while the window is open. Forever's interface hides unlearned recipes (`Camelot/Blizzard_Professions.lua`), so the DB2 is the catalog. Reagents and amount from the game win over the DB2.
- **Profit** = lowest AH price × amount × 0.95 − reagents. Reagents at the cheaper price from AH and vendor: first vendor prices seen in the game (unlimited ones only), otherwise `VENDOR_ITEMS` (vials, spices, threads, dyes, flux …) with `BuyPrice / VendorStackCount`. Own reagents count at the market price. Bound results and results without an AH price count at the vendor sell price. Notes appear when the price is older than the last scan, the lowest price is below 60 % of the median of the last 7 scan days or a reagent has no price.
- **Profit history** (`profit_history`, `trend_of`; fields `history` and `trend` per recipe): the same profit on the last 8 full scan days. A day counts as a full scan if it has at least 30 % of the entries of the biggest scan day (Auctionator also writes day prices for single searches). Auctionator stores per day only the highest (`h`) and lowest (`l`) minimum price; the day price is the middle, on the last scan day the current minimum price, so that the last point equals the profit shown. Days without a price for the result or a reagent are missing. Trend = change over the last three scan days, below 20 % counts as stable. For "falling", the note "profit is falling (on … still …)" replaces the note "cheap right now". Background: in the first weeks after launch the profit of freely craftable potions fell to about zero within 3 to 5 days as soon as many had the recipe; only what a cooldown limits stayed stable (transmute Arcanite). Auctionator does not know sales volumes.
- **Missing recipes:** The source is a recipe item in the AH (price, offers), a recipe seen at a vendor, a recipe item "not in the AH" (drop, reputation or vendor, unknown) or the trainer (no recipe item, `AcquireMethod` ≠ 3; `AcquireMethod` 3 without a recipe item counts as not obtainable). Learnable: recipe item with `RequiredSkillRank` ≤ skill; at the trainer certain if "yellow" ≤ skill (the required skill is never above yellow), otherwise unknown. "Pays more" = more profit than the best learned recipe with at least 3 offers. Sorted first by "learnable now", then by profit.
- **Not considered:** multi-step crafting (intermediates count at the AH price), trainer costs (not in the DB2), AH deposit, faction restrictions of recipes. The app knows vendor prices for recipes only once the addon has seen the vendor.

## Consumables (`sim/tools/consumables`)

- **Catalog** from the DB2 tables (`build_catalog`, stored as `scripts/cache/consumables-<build>-<locale>.json`; raise `CATALOG_VERSION` when the structure changes): every item of `Item.ClassID` 0 with its spell (`ItemEffect` + `ItemXItemEffect`), decoded from `SpellEffect` (`decode`): effect 10 = heal, 30 with misc 0 = mana (range = base points × (1 ± `Variance`/2), e.g. Healing Potion 320 → 280–360), aura 84/85 in food (subclass 5) = health/mana per 5 s for the duration (`SpellMisc.DurationIndex` → `SpellDuration`), aura 8 in bandages = heal per period, effect 54 = temporary weapon enchantment (`SpellItemEnchantment`: type 3 = equip spell, decoded again; type 5 = stat), other auras through `AURA` (13 spell damage by school mask, 29 attributes, 34 health, 85 mp5, 57 spell crit, 290 crit, 674/22 armor, …). Skipped: conjured items (`Flags_0` & 2) and names with "Deprecated", "Test" and similar.
- **Forever's buff food:** "Nutritious Food" triggers the eating spell (effect 64) and, after 10 s, Well Fed through aura 227; the amount is on the outer effect (`$s2`, e.g. Nightfin Soup +22 spell damage), the Well Fed aura itself holds 1. Some Well Fed spells also mention an XP bonus (spell 1243969, depends on a player condition); it is not shown.
- **Usable:** `RequiredLevel` ≤ level, `AllowableClass` contains the class, required skill reached (bandages ask for skill line 2942, which counts as First Aid 129).
- **Listed** are items the character can get at all: in bags or bank, in the AH, at a vendor (seen by the addon, or `VENDOR_FOOD`: bread, meat, fish, cheese, fruit, mushrooms and water every innkeeper sells, at `BuyPrice / VendorStackCount`) or made by a profession (recipe catalog of `tools/recipes`). "Best now" = the strongest one available now (owned, sold or with a learned recipe). Items with the same effect are merged into one row ("same effect") unless they are owned or craftable by the character. "Next" = the stronger item with the lowest required level (or skill) above the character.
- **Relevant stats** per class in `RELEVANT` (casters: spell power, intellect, spirit, mp5, stamina, spell crit, warlock also shadow and fire; melee: strength, agility, attack power, crit, armor; Paladin, Shaman, Druid everything).
- **Catalog for the fight (`CATALOG_VERSION` 2):** per item also `cat` = the cooldown category (`ItemEffect.SpellCategoryID`, else `SpellCategories.Category` of its spell), `auras` = the spells whose aura is the buff (to find it among `character.buffs`) and `healthCost` (effect 2 = damage of the item's own spell, when it restores something: Dark Rune 800 for 900–1500 mana). Eating and drinking are recognized by the category (11 food, 59 drink) whatever the subclass says (rations of subclass "other"). `EXTRA_ITEMS` brings in the Demonic and the Dark Rune (12662, 20520), which the game files as trade goods (class 7).
- **Consumables for a fight** (`fight_plans`, `plans[]` in the answer; needs the combat engine, `compute(engine="auto"|"on")`): every usable, obtainable consumable gets a kind (`fight_kind`: `flask`, `elixir`, `food` = Well Fed, `weapon` = temporary weapon enchantment, `scroll`, `potion` = category 4 or subclass potion, `rune` = category 1153, `other`; eating, drinking, bandages and a buff without a duration are none), the slots it occupies (`fight_slots`) and a stat delta over the fight (`fight_delta`, the engine's keys through `ENGINE_KEYS`): a buff counts for the share of the fight it lasts (a 30 s potion buff in 60 s: half), the mana and health of a potion or rune as mana and health per 5 s over the fight (`uses_in`: one use at the start and one every 2 minutes), a rune's health cost as negative hp5, maximum health as stamina. The engine rates each delta alone (`gain`, with `reoptimize`), then `choose` builds the best set greedily: always the available row that adds the most on top of the set so far (`adds`), among those whose slots are free; of two that add the same the owned one, then the cheaper one; it stops when nothing adds 0.05 or more. A row whose slot the set holds has `blockedBy` (the name). A buff that was on the character at the snapshot (`character.buffs` against the item's `auras`) is in the sheet's numbers and holds its slots: the rows of those slots carry `onYou` (the buff's name) and are not chosen. If only one consumable gives the buff, its row is `active` and adds nothing; a buff many items give (Forever's Well Fed is one spell for every meal) does not say which item it was, so those rows keep what they would add alone. Health an item costs (`healthPerSec`): what costs more than half of the health pool is `tooCostly` and never in the set (`MAX_HEALTH_COST`; a Dark Rune takes 600–1000, Siegfried has 815 health); for the healing metric the cost per second is taken off what the item adds (somebody has to heal it, as the engine does with Dark Sacrifice), for the damage metric it is in the delta as health lost, which a warlock's Life Tap budget feels. A plan: `{metric, unit, title, seconds, targetDelta, base, value, gain, gainPct, cost (one of each chosen item not owned), unpriced, chosen[], kinds[] = {key, label, rule, assumed, items, more}, delta (the set's summed delta), engine, active[] (the names of the buffs that were on the character)}`. One plan per metric of the class without `ttoom`, the spec's own first; the whole run takes about 2 s.
- **What works together** (the slots; `KINDS` carries the rule and, where it is one, the assumption as text):
  - *Flask:* one at a time; the flask's own spell text says so. Next to elixirs, food and oil.
  - *Elixirs:* the spell texts have no battle and guardian wording, and all elixirs and flasks share one item cooldown category (2593) that is only the 3 s use cooldown. The set takes one elixir per stat (`elixir:<stat>`); that two for the same stat do not add up is an **assumption** (a guide calls it "not confirmed", another says flasks now work next to elixirs).
  - *Buff food:* one Well Fed at a time.
  - *Weapon oil:* one temporary enchantment per weapon; Spellstone and Firestone take the same place by their texts (they are conjured and not in the catalog).
  - *Scrolls:* one per stat. **Assumption:** the scroll counts in full; in the original game it did not add to the class buff of the same stat.
  - *Potions:* all share category 4 with a cooldown of 2 minutes, so one potion slot: a mana potion and a spell power potion exclude each other.
  - *Runes and roots:* category 1153 with its own 2 minutes, next to the potions.
  - *Other buffs:* the Blasted Lands buffs share category 103 (1 h), the Zanza potions category 79; for the rest nothing is known and each counts on top (**assumption**).
- **The set by value** (`sim/tools/consumables/value.go`, `chooseValue`; `--set value`, the page's "Set: best value per gold"): the same candidates, kinds and slots, built by what a step adds per gold instead of by what it adds.
  - *Gold* is what an hour of fighting costs with the item (`costPerHour`, copper): its price times the items an hour takes. A buff takes one item per duration (a flask of two hours half its price, an elixir of 30 minutes twice its price; a buff shorter than the fight one per fight), a potion or a rune the ones a fight uses (`uses_in`) in every fight, so 60 an hour in fights of a minute. What is in the bags costs nothing. This is what makes a flask comparable with a potion; the plan's `cost` stays "one of each item not owned".
  - *Steps:* the set grows one step at a time. A step puts one item in; the items of the set that share a slot with it go out, and the step is rated by what the metric gains (the engine rates the whole new set, with `reoptimize`) for what the hour costs more. Steps that cost nothing come first (the bigger gain first: what is in the bags), then the one with the most gain per gold. So the cheap item of a kind is taken first, and a stronger one replaces it later, when its extra gold buys more there than anywhere else. A step must add 0.05 or more and, with `--budget` (gold per hour), fit what is left of it; when none is left the set is done. Every step raises the metric, so it ends; without a budget it ends at about the strongest set (the same items for Malgruk).
  - *Answer:* a plan of this mode has `mode: "value"`, `costPerHour` (the set's), `budget` (copper, or null) and `steps[] = {n, item (the row), adds, costPerHour (of the step: what the hour costs more, negative when the item is cheaper than what it replaces), perGold (null for a step that costs nothing), value and spent (the metric and the cost per hour after the step), replaces[] = {id, name, quality}, replacedBy (the name of the item a later step puts in its place, or null)}`; `chosen[]` is the set at the end, in the order the items came in. A row also has `costPerHour` and `perGold` (its gain alone per gold; none for an item in the bags or without a gain), `addsPerGold` for a row of the set, `noPrice: true` (an item from an own recipe that nobody sells: no price, so never in this set; the strongest set counts it as free) and `overBudget: true` (it would add something, the budget does not pay for it). The rows of a kind come in the order: in the bags, then by `perGold`, last what has no price. The strongest set's answer has none of these keys.
  - *On 2026-11-23 (60 s, +2 levels):* Malgruk (level 57) 354.7 → 548.9 DPS in 19 steps for 86g 91s an hour: the fish and the intellect elixir from his bags (+15.4), then Minor Arcane Elixir 89 DPS per gold an hour and Minor Wizard Oil 64, each replaced step by step by the stronger ones (Wizard Oil 23, Greater Arcane Elixir 8.7), the +28 spell power stew for the fish 12.1, Flask of Supreme Power +95.5 for 9g 05s an hour = 10.5 per gold (ahead of the Elixir of Shadow Power, 8.6, although the flask costs twelve times as much to buy), and last the spellblasting potions, which cost 72 gold an hour for +15 DPS (0.1 to 2 per gold). Up to the flask the set costs 10g 31s an hour for 497.9 DPS; with a budget of 3 gold an hour it ends at 412.4 DPS. Siegfried's healing set is seven items from his bags (+48 HPS) and two scrolls for 4 silver an hour.
  - *Not in it:* the stock (one potion in the bags counts as free for the whole hour); the order is greedy, so with a budget a different choice can add more (a set that leaves out two weak steps to afford one strong one); a fight shorter than the potion cooldown still counts a potion in every fight; upgrades and rotations "with consumables" and the lists in the game keep using the strongest set.
- **In the other calculations:** `fight_buffs(wow, char, metric, fight_seconds, target_delta)` returns the best set as `{delta, names, gain, unit, metric, text}`; `upgrades.compute(with_consumables=True)` and `rotations.compute(with_consumables=True)` (CLI and bridge `--consumables`, the checkbox "with consumables" on both pages) start the engine with that delta as `buffs`. The upgrades then rate the gear under the set (more spell power raises the value of hit and crit, more mana lowers that of intellect); the guide plays every fight under the set of the normal fight.
- **On 2026-11-21 (60 s, +2 levels; Malgruk's snapshot without a food buff, a later one with Well Fed on reads 328.6 → 502.4 and leaves the meal out):** Malgruk 304.4 → 497.4 DPS (+63 %) for 22g 21s: Flask of Supreme Power +93.8, Elixir of Shadow Power +25.0, Greater Arcane Elixir +21.9, a +28 spell power meal +17.5, Wizard Oil +15.0 (Brilliant Wizard Oil would add +25.5, none in the AH), the +33 spellblasting potion +10.3, Elixir of Greater Intellect +8.1, Scroll of Intellect IV +1.4; a Dark Rune adds 4.8 alone and nothing in the set (Life Tap already covers the mana). Siegfried (level 28) healing 132.1 → 180.1 HPS (+36 %) for 6s 45c, most of it already in his bags: Mana Potion +19.5, a +10 intellect meal +7.5, a +20 healing elixir +6.1, Minor Mana Oil +5.8, Scroll of Intellect II +4.0, a +6 intellect elixir +2.2, a +6 mp5 elixir +1.7 (a Dark Rune would add 25.8 after its health cost, but it takes about as much health as he has); damage 64.3 → 80.7 DPS.
- **Not considered:** resistance and protection potions, utility (speed, water breathing), rogue poisons, sharpening stones without a stat, healthstones (conjured). In the fight: none of the stacking rules is tested in the game; with a rune in a healer's set the upgrades and the rotation guide "with consumables" show the healing before the rune's health cost (the plan shows it after); the cost is one of each item whatever it lasts (a flask two hours, a potion one fight); the rotation guide uses the set and a potion's share of the normal fight for every fight (a rune's mana per second is then too high in the long fights and too low in the short one); a weapon oil already on the weapon at the snapshot is not recognized (it is no buff in `character.buffs`), so the oil would count twice; melee crit and haste on a consumable have no engine key; the set is greedy, not proven optimal (with gains that only shrink on top of each other it rarely differs).

## Notes

- Item export (addon since 1.1): the candidates come directly from `Auctionator.Database.db` (all equippable armor and weapons of the last 4 scan days). It is stored account wide and incrementally per client build and language. `/wowmcp items full` reads everything again, for example to get tooltip colors.
- Make changes to an addon in the checkout of the addon repo (`~/work/WoWMCP`, `~/work/GoldPerHour`), test and commit there. It reaches the game through a release (raise the version and push, see "CI and releases") or, for trying it out, through a local source of the app. Checks:
  - `uv run tests/test_addon.py` in the addon repo: the addon in Lua 5.4 against a stubbed WoW API, in both languages. The game runs Lua 5.1 with its own API, so a change still needs a look in the game.
  - `wow_lua_lint` with `flavor: forever` only accepts paths under `_retail_\Interface\AddOns`. Copy the file briefly to `_retail_\Interface\AddOns\_wowmcp_lint_tmp\` (without a `.toc`, it is not loaded) and delete it afterwards. `knownGlobals`: `WoWMCP_Char`, `WoWMCP_Items`, `WoWMCP_Account`, `WoWMCP_AppRequest`, `WoWMCP_AppData`, `WoWMCPListFrame`, `Auctionator`, `AuctionatorTabs_Shopping`, `ReloadUI`.
