### CI and releases

Releases are automatic in all three repos: **raise the version, commit, push to `main`**. Nothing else is needed; never create tags or releases by hand unless a workflow failed.

| Workflow | Runs on | Does |
| --- | --- | --- |
| `ci.yml` | every push to `main` and every pull request | runs the tests and builds the package. On `main`: if the version has no tag `v<version>` yet, it creates the tag and starts `release.yml` for it (a tag pushed with the workflow token does not start workflows by itself, hence `gh workflow run release.yml --ref <tag>`). |
| `release.yml` | a tag `v*` (pushed by hand or started by CI) | checks that the tag matches the version, tests and builds again from the tag, publishes the GitHub release |
| `build.yml` (this repo only) | called by the two above | tests on Ubuntu and Windows (`npm test`, every `scripts/test_*.py` and `server/test_*.py`), then the Windows installer: copies `uv.exe` into `app/build/bin`, `npm run dist`, starts the built app once in capture mode against `scripts/fixtures/goldperhour` (`--require=connection,goldperhour`) and checks that the bundled uv answered. Artifacts: `installer`, `screenshots`. |

- **Addons:** packaged by [BigWigsMods/packager](https://github.com/BigWigsMods/packager) (`.pkgmeta`: no README and no tests in the zip; the zip holds the folder `<Name>/` with a generated `CHANGELOG.md`). `tests/check_package.py` checks the zip. The release has the assets `<Name>-v<version>.zip` and `release.json`.
- **CurseForge and Wago (addons):** the release workflow uploads there as soon as the project id is in the `.toc` (`## X-Curse-Project-ID: <id>`, `## X-Wago-ID: <id>`) and the repository secret is set (`CF_API_TOKEN`, `WAGO_API_TOKEN`; `gh secret set CF_API_TOKEN --repo kejith/<Name>`). Until then the upload is skipped. Creating the projects and choosing a license is a manual step on the sites; the repos have no `LICENSE` file yet. Details are in the README of each addon. CurseForge and Wago host addons only, so the desktop app is published on GitHub.
- **App:** `softprops/action-gh-release` publishes the installer with `SHA256SUMS.txt`; the text above the commit list comes from `.github/release-notes.md`. The installer is not code signed.
- **Action versions in use:** `actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7`, `actions/download-artifact@v8`, `softprops/action-gh-release@v3`, `astral-sh/setup-uv@v10.3.3` (setup-uv has no moving major tag), `BigWigsMods/packager@v2`.
- **Watching:** `gh run list --repo kejith/<repo>`, `gh run watch <id>`, `gh release view --repo kejith/<repo>`.

### Addons from GitHub releases

The app does not bundle the addons. `addonInfo` and `installAddon` take the files from a source:

1. **A local checkout**, if one is set: `addonSources` in `settings.json` (`{ "wowmcp": "<folder>", "goldperhour": "<folder>" }`) or the environment variables `WOWMCP_ADDON_DIR` and `GOLDPERHOUR_ADDON_DIR`. Under Windows for example `\\wsl.localhost\orebound\home\rick\work\GoldPerHour`. This gets a change into the game without a release. The card shows "local folder".
2. **Otherwise the newest release** of `kejith/WoWMCP` or `kejith/GoldPerHour`. The app asks GitHub every 15 minutes at most (anonymous clients get 60 requests per hour), "Check for updates" asks right away. The zip is unpacked in the app's data folder (`%APPDATA%\wowmcp-app\addons\<Name>\<Tag>`, in WSL `~/.config/wowmcp-app/addons`), older downloads are deleted.
3. **Without a network** the release downloaded last applies; the card shows "not checked, as of …" with the reason on hover. Without a network and without a download the app cannot install anything and says so.

"Update available" means: at least one file of the source differs from the installation. If the installed version is higher than the source's (installed from a checkout), the addon counts as current ("newer than the source").

## Languages

Addons, scripts and app work with an English and a German client and follow the client's language. Other clients get English.

- **Principle (gettext style):** the English text is written where it is used and is the key; German is a catalog; a missing entry falls back to English. Names from the game are never translated: they come in the client's language from the addon export and the DB2 tables.
- **Scripts:** `scripts/i18n.py`: `tr("text {n}", n=3)`, `mark("text")` (translated later), `set_language(lang, wow)`, `client_locale(wow)`, `short_date()`. Language: `--lang auto|en|de`, else the environment variable `WOW_TOOLS_LANG`, else `textLocale` from `WTF/Config.wtf` (`deDE` → German, anything else English). Catalog `scripts/locale_de.py` (`TEXT`). `scripts/test_i18n.py` walks the syntax tree of every script and fails on a text without a German entry, an unused entry or different placeholders.
- **App, main process:** `app/i18n.js` (`t('text {name}', {name})`, `setLanguage`, `clientLocale(wowDir)`, `languageOf(locale)`), catalog `app/locales/de.js`. `addon.js` and `releases.js` use it for their error messages.
- **App, window:** `app/renderer/i18n.js` (`t`, `mark`, `locale()` → `en-US`/`de-DE` for numbers and dates), catalog `app/renderer/locales/de.js`. Static texts in `index.html` carry `data-i18n="English text"` (or `data-i18n-title`, or `data-i18n-help` for the text behind a "?" button); `applyLanguage()` in `renderer/app.js` fills them. Texts that contain HTML (`<code>`, `<b>`) are inserted as they are, everything else goes through `esc()`.
- **App language:** `--lang=en|de` on the command line (captures) wins, then `language` in `settings.json` (`auto`, `en`, `de`; the select box in the sidebar), then the client's `textLocale`, then the language of the operating system. The main process passes `--lang <en|de>` to the bridge, so app and scripts always agree.
- **`app/i18n.test.js`** (part of `npm test`) scans `t(…)`/`mark(…)` and `data-i18n`, `data-i18n-title`, `data-i18n-help` for texts without a German entry, unused entries, different placeholders or HTML tags, and fails on umlauts in code outside the catalogs.
- **Game texts the scripts parse** exist in both languages: tooltip lines ("Equip:"/"Anlegen:", "Use:"/"Benutzen:", hit and crit percent), the Life Tap text, skill requirements. German regular expressions in `upgrades.py` and German test data are intended.
- **Tables with text** (`ItemSparse`, `SpellName`) are downloaded and cached per client locale: `scripts/cache/<Table>-<build>-<locale>.csv`, the recipe catalog as `recipes-<build>-<locale>.json`. Names of writs and crate items for both languages are in `scripts/data/item_names.json`.
- **Addons:** texts in `Locales.lua` (English default, a block per `GetLocale()` code). The export has `client.locale`.
- **Adding a language:** a catalog per part and its code in `LANGUAGES` of the three `i18n` files; for the addons a block in `Locales.lua`.

## Desktop app (`app/`)

Electron app "WoW Forever Tools" (Electron 45, no build step, vanilla JS) that brings addon, scripts and SavedVariables together. It runs locally and has no server. It writes into the game folder in two places, both inside the addon folders: the requests (`AppRequest.lua`) and the lists for the game (`AppData.lua`, see "Lists in the game"). It uses the network in two places: the bridge downloads game tables and an item icon the first time they are needed (wago.tools, only table names, FileDataIDs and the build number), and the main process asks GitHub for the newest release of the two addons (see "Addons from GitHub releases").

**Start from source:** `cd C:\Coding\wow\app`, then `npm start` (`npm install` only after a fresh clone). Needs Node.js and uv. If the game is somewhere else, set `WOW_FOREVER_DIR`. Fixed settings come from `%APPDATA%\wowmcp-app\settings.json` (`wowDir`, `uvPath`, `addonSources`, `language`, `sendToGame`). The file exists only once it is created; the user interface has controls for the language and for `sendToGame` (the switch of the card "Lists in the game"). The data folder kept its name `wowmcp-app` when the app was renamed.

**Installed app:** electron-builder (`build` in `app/package.json`) packs `*.js`, `locales/` and `renderer/` into `app.asar` and puts next to it, under `resources/`, the scripts (`scripts/*.py` without tests, `scripts/data/`) and `bin/uv.exe`. `main.js` separates the two cases with `app.isPackaged`: `ROOT` is `process.resourcesPath` instead of the repo, the bundled uv is tried first, and downloaded game data goes to `%APPDATA%\wowmcp-app\game-data` (handed to the bridge as `WOW_TOOLS_CACHE`) instead of `scripts/cache`. The folder must not be called `cache`: Chromium keeps its own `Cache` in the same place and Windows ignores case. On the first start uv downloads Python, lupa and Pillow; the bridge may take up to 300 s for that. The icon is `app/build/icon.png`. `app/build/bin/` is not versioned (CI copies uv there; for a local `npm run pack` copy `~/.local/bin/uv` to `app/build/bin/uv`).

**Explanations and tooltips:** A page shows numbers and names; what a number means sits behind a "?" (`help(html)` → `<button class="help" data-help>`). Any element with `data-help` opens the one popover `#pop`: on hover and keyboard focus, a click on a "?" pins it, Escape, scrolling or a click elsewhere closes it. `helpAttr(html)` takes HTML (escape the texts yourself), `hintAttr(text)` plain text and replaces the native `title`, which shows late and cannot be styled. Where the "?" goes: tables that repeat (writ tiers, crate tiers, slot cards, consumable cards) get one "?" at the section heading with a definition list (`terms([[term, text], …], foot)`); a single big table (recipes, shopping list) gets it in the column headers (`th([label, cls, info], …)`); an option gets it next to its label (`<span class="label">`). Do not add explanatory paragraphs below a table.

**Saved view:** The window remembers the page, the character and the options of the pages (`state.writs`, `upgrades`, `recipes`, `consumables`, `prices`) in `localStorage` (`wow-forever-tools:view`) and restores them at the next start; a value whose type does not match the default is ignored. Not in capture mode, so screenshots always show the defaults.

**App ↔ addon:** Addons have no file or network I/O. The app writes requests to `Interface\AddOns\WoWMCP\AppRequest.lua` (`WoWMCP_AppRequest = { id = <unix time>, action = "items"|"sync", full = true? }`). The game reads the file on `/reload`, the addon runs every request once per `id` (3 s after logging in) and writes the result to `WoWMCP_Account.lastRequest`. The app sees that on the next `/reload`. Forever also re-reads the `.toc` on `/reload`: new files and new SavedVariables load without restarting the game (tested in the game on 2026-11-15). Caution: `/reload` first saves with the old code and then loads the new one. After an addon update it therefore takes a second `/reload` until data in the new format is on disk.

**Lists for the game** go the same way in a second file, `Interface\AddOns\WoWMCP\AppData.lua` (`WoWMCP_AppData`), which the app rewrites whenever its results change; see "Lists in the game".

## Lists in the game (`scripts/ingame.py`, `Lists.lua` in the addon repo)

The addon shows the app's results in the game. Addons cannot read files, but the client loads every Lua file of the `.toc` on `/reload`; so the app writes a Lua file into the addon folder, as it does for requests.

- **Flow:** AH scan → `/reload` (the game saves) → the app's watcher fires, the bridge computes all four pages for every character and writes `AppData.lua` → second `/reload` (the game loads it). The file is written in one step and only if its content changed (`hash`), only into an installed WoWMCP whose `.toc` lists `AppData.lua` (1.7 or newer).
- **File:** `WoWMCP_AppData = {version = 1, generated, hash, locale, scanDate, chars = {[first name] = {level, lists, tips, vendor, errors?}}}`. A list is `{key, title, note, sections = {{title, note, rows}}}` with the keys `upgrades` (only for a Warlock, the scale knows no other class), `writs`, `crates`, `recipes`, `consumables`; a row is `{id, name, q (quality), n (amount), info, price (copper), shop (goes to the shopping list), sub (indented: belongs to the row above)}`. `tips[itemID]` = up to 4 tooltip lines, `vendor[itemID]` = the chat line for a recipe a vendor sells. Money inside a text is `{m:<copper>}` and becomes coins in the game; `|` is doubled. `version`, `generated` and `hash` come first, `file_state()` reads them from the head of the file. Texts are in the client's language whatever `--lang` says; `hash` covers everything but the time.
- **Window** (`WoWMCPListFrame`, built when first needed): one tab per list, 16 rows at the default size, mouse wheel and slider. Resizable through the grip at the bottom right (600×400 to 1600×1200, right-click: default size); `layout()` in `Lists.lua` and `ns.history.layout` fit rows, info column, result list and plot to the size, which is saved in `ui.size`. A click on a row searches the auction house for the item (Auctionator's shopping tab if Auctionator is there, otherwise the search box of the Blizzard frame), a modified click goes through `HandleModifiedItemClick` (shift: link into the chat or the search box, ctrl: dressing room). "Search the shopping list" searches all `shop` rows of the tab at once. It opens with the auction house (`/wowmcp ah off` turns that off) and with `/wowmcp show`; Escape closes it.
- **Auctionator shopping lists:** per list one list "WoWMCP: <title>" with the `shop` rows of the logged-in character (`Auctionator.API.v1.CreateShoppingList`, search strings through `ConvertToSearchString`, at most 60, names with `;` or `^` are skipped). Synced 5 s after login and when the auction house closes, never while it is open (Auctionator would start searching), and only if the data changed (`ui.synced` = `hash:character`). Lists of an earlier sync that no longer exist are deleted.
- **Tooltips:** `TooltipDataProcessor.AddTooltipPostCall(Enum.TooltipDataType.Item, …)`, with `OnTooltipSetItem` as fallback, only on `GameTooltip` and `ItemRefTooltip`, light blue lines.
- **Loaded?** The addon notes what it loaded in `WoWMCP_Account.appData`, which the app sees one `/reload` later. So the app also counts the file as loaded if the account SavedVariables are newer than `AppData.lua` (the game saved, so it reloaded, after the file was written).
- **Not verified:** nothing of this has run in the game yet. The addon runs in the Lua simulation of its tests (also against a real `AppData.lua`), where widgets answer unknown methods with nothing; so the layout of the window, the Auctionator calls and the tooltip hook still need a look in the game. Lint with `flavor: forever` reports `GetMoneyString` and `HandleModifiedItemClick` as unknown; both are Lua functions of Forever's FrameXML and are guarded.

## GoldPerHour (repo `kejith/GoldPerHour`, `scripts/goldperhour.py`)

- **Addon:** Window with gold and gold per hour for herbs and loot. Herbs = loot right after Herb Gathering (spell 2366, a spell of the same name or `/gph herbid`) from a world object, everything else is loot. Items count at the Auctionator price (otherwise the vendor price; grey and bind-on-pickup always vendor), coins from the loot window directly. `GetTime()` does not survive a logout, so the session pauses when saving.
- **Since 0.3 for the app:** `GoldPerHourDB.session` = `{started, lastActive, zones[zone] = copper, chars[name] = true, samples = {{t, herbs, loot}, …}}` (a point every 5 min of session time through `C_Timer`, plus at start and stop; above 288 points it is thinned out). Reset (button, `/gph reset`, request) moves the session to `history` (at most 100, items as `{id, name, quality, count, value}`). `settings` = `scale`, `tooltipItems`, `priceSource` (`auctionator`/`vendor`), `resumeAfterReload` (default on), `autoStart` (the first loot window starts the session); `hidden` and `herbSpells` as in 0.2. `resume` remembers at logout whether the session was running: on `PLAYER_ENTERING_WORLD` with `isReloadingUi` it continues, on a real login it does not. `updated` = time of saving, `lastRequest = {id, action, done, settings, error}`.
- **Requests:** `Interface\AddOns\GoldPerHour\AppRequest.lua` with `GoldPerHour_AppRequest = { id, action = "start"|"stop"|"reset" (optional), settings = {…} (optional) }`. Run at the first `PLAYER_ENTERING_WORLD` after loading (after resuming), every `id` once (`lastRequestId`). The addon checks the settings again (type as the default, scale 0.5–2, tooltip 1–30).

## Upgrade rating (`scripts/upgrades.py`)

The principle is Pawn's: a weight per stat, the unit is 1 point of shadow spell power. Two things go beyond a fixed Pawn scale: the weights for hit and crit are derived from the character (`build_scale`), and what is rated is always the whole set (`set_value`, gain = value after the swap minus value before). So hit counts only up to the cap. With `--engine on|auto` the combat engine (see below) replaces this scale: gains are then the simulated DPS change of each swap.

- **Stat keys in Forever:** Hit and crit exist only as a shared rating for melee and spells (`ITEM_MOD_HIT_RATING_SHORT`, `ITEM_MOD_CRIT_RATING_SHORT`; tooltip "Improves your chance to hit by 1.0%", German "Verbessert Eure Trefferchance um 1.0%"). The percent values are in the tooltip, otherwise they are converted (10 and 14 rating per 1 %, `learn_ratings` measures that from the export). `norm_stats` translates everything into `sp`, `stamina`, `intellect`, `spirit`, `mp5`, `hp5`, `armor`, `wand_dps`, `hit`, `crit`. Healing, other schools, spell penetration and melee stats count 0.
- **Profiles** (`PROFILES`): `leveling` (enemies up to +2 levels; spirit 0.25, mana/5s 0.7, wand DPS 0.6) and `dungeon` (bosses +3; 0.05/0.3/0.1). Automatic: `leveling` below level 60. These weights are fixed rules of thumb.
- **Intellect and stamina** are computed from level, stats and talents (only if the export has health and mana, otherwise the fixed values 0.35/0.5 and 0.25/0.25 apply). Pool = mana + health × Life Tap ratio. 1 mana = `mana_share` × (13 × level + spell power) / pool points, 1 health for survival = `survival_share` × (13 × level + spell power) / health. Int = 15 mana + crit per int × crit weight, stamina = 10 health × (Life Tap ratio × value per mana + survival value). `mana_share`/`survival_share` are rules of thumb (`leveling` 0.10/0.05, `dungeon` 0.06/0.02), chosen so that Malgruk at level 46 lands roughly at the old fixed weights. A bigger pool lowers the value of each point; at a low level int and stamina count more because spell power matters less there. The values from the character stats apply at the time of the snapshot, so with the buffs active at that moment.
- **Crit from intellect:** since addon 1.3 from the game (`critFromIntellect`), before that estimated as (spell crit − 1.7 % − crit of the gear) / int. For Malgruk (level 46) the estimate matched on two snapshots with 96 and 149 int: 0.0224 % per int, so about 45 int for 1 %. Life Tap ratio from the spell text ("X health … Y mana"), otherwise 1:1; Improved Life Tap +10 % per rank. Life Tap is in wago.tools' `SpellEffect` by now (ranks 1454, 1455, 11688, 11689; an earlier note here said it was missing).
- **Hit:** miss chance against +0/+1/+2/+3 levels = 4/5/6/17 % (from Forever's character display, `Camelot/PaperDollFrameStats.lua`). Cap = miss − 1 % − the character's `spellHit` (`GetSpellHitModifier`, without gear; Malgruk has 5 %). While leveling the cap is thus reached and hit counts 0. In the profile `dungeon` every percent up to the cap counts like 1 % damage. Suppression is part of `spellHit`: in Forever it gives 1 % hit per rank to every spell (trait tables; until app 1.9.1 the scale added the Classic 2 % per rank for Affliction spells on top).
- **Crit:** 1 % damage = (13 × level + shadow spell power) / 100 points; 1 % crit = that × 0.5 (crit bonus) × the share of the damage that can crit (25 %, with Pandemic 3/3 85 %).
- **Checked in the game:** with Pandemic the DoTs crit (the player, 2026-11-20). **Assumptions not yet checked:** 1 % miss always remains (Classic value); Improved Life Tap gives +10 % per rank and is not already included in the Life Tap text. The addon exports the talent texts since 1.12.
- **Comparison:** rings and trinkets against the weaker of the two slots, two-handers against main hand + off hand, an off-hand item with a staff equipped against the staff. Special effects (`special_effects`: "Use:" and "Equip:" lines that are not a stat from `stats`) cannot be rated by the scale; such items with less than 5 points of gain are listed under "With a special effect, please look for yourself".
- **Package** (`best_package`): knapsack problem with at most one option per slot group (ring pairs, trinket pairs, main hand + off hand as a combination), without items above the own level. Budget = `--max-price` or the own gold. The list is sorted by points per gold; a smaller budget has its own optimum, which is not always the beginning of this list.

## Combat engine (`sim/`, `scripts/simengine.py`)

A per-class combat model in Go (module `github.com/kejith/wow-forever-tools/sim`, binary `simforever`), built after the research of 2026-11-20 (WoWSims for the architecture — MIT, see `sim/THIRD_PARTY.md` before porting code; timhul/ClassicSimForever for the data-driven idea — no license, concepts only). Stage 1 evaluates a priority rotation as a closed-form steady-state cycle; Stage 2 (`method: "montecarlo"`) plays the same rotation cast by cast with real rolls.

- **Split:** Python keeps everything that needs SavedVariables or localized tooltips (candidate filtering, slot logic, hit/crit percent from tooltips); the engine is pure compute. One `upgrades.compute()` makes three engine runs (`value_batch`): candidate swaps + per-slot removals, the pair/weapon combos, the package prefixes — each run is one JSON bundle on stdin, one answer on stdout (errors in the payload, exit 0, like `app_bridge.py`).
- **Data:** the engine reads the DB2 CSVs from the shared cache (`scripts/cache` or `WOW_TOOLS_CACHE`; `simengine.py` downloads them through `icons.table` first): SpellClassOptions (which spells belong to the class), SpellEffect (base points, per-level scaling, `EffectBonusCoefficient` — Forever bakes the cast-time coefficient per rank into it, verified on Shadow Bolt), SpellMisc/SpellCastTimes/SpellDuration/SpellPower/SpellLevels/SpellCooldowns, SkillLineAbility (the class's spells, `AcquireMethod`), SpellName (localized labels, plus the `enUS` table for the rank chains), and the trait tables TraitDefinition, TraitDefinitionEffectPoints and CurvePoint (talent values per rank, see "Talents"). Character numbers come from the snapshot sheet (they already include gear and buffs); items enter as canonical stat deltas (`simengine.KEY_MAP`), so intellect and stamina work through `manaPerIntellect`/`critFromIntellect`/`hpPerStamina`.
- **Rank chains** (`catalog.buildChains`): Forever leaves `SkillLineAbility.SupercedesSpell` empty for most class spells (678 of 7853 rows have it), so the ranks of a spell are the class's SkillLineAbility spells with the same English name and the same `SpellClassMask`, plus the explicit links that exist, ordered by `SpellLevels.SpellLevel`. The English name is the key because a translation may name the ranks of one spell differently (deDE: Smite rank 1 "Heilige Pein", ranks 2+ "Göttliche Pein"); `simengine.py` therefore also downloads `SpellName` in `enUS` (`catalog.ReferenceLocale`), without that file the localized names are the key. `AcquireMethod` 3 marks a granted version of a rank (a talent's cast, e.g. the second Renew row 425268–425277): it shares the rank number of the trained rank of its level and is not part of the assumed spellbook. Checked against the spellbook export: all 136 "Rank N" lines of Siegfried and Malgruk match. Until app 1.9.0 the chains came from `SupercedesSpell` alone, so every release from 1.5.0 to 1.9.0 rated with rank 1 of every spell (Siegfried 91 instead of 111 HPS, Malgruk 105 instead of 124 DPS). The same releases also read the equipped wand's damage per second from a key the snapshot does not have, so the time on the wand counted 0 (fixed in 1.9.1; a test pins the bundle value).
- **Talents** (`sim/talents`): Forever has one spell per talent, and its `SpellEffect` row holds a single value (often the first rank's, sometimes none). The exact value of every rank is in the trait tables: `TraitDefinition` (talent spell) → `TraitDefinitionEffectPoints` (`OperationType` 0, per effect index a curve) → `CurvePoint` (`Pos_0` = rank, `Pos_1` = value); `catalog.TalentValue` reads them. Without the three tables in the cache the engine falls back to the single value in `SpellEffect` (the rules of the overrides file to their `perRank` × rank) and says so (`coverage.talentValues: "basepoints"`, the app shows a notice). The talent spell's auras are decoded generically: 79 (percent damage per school), 72 (percent mana cost per school), 107/108 (flat/percent spell modifiers with class-mask filter), 134 (regeneration while casting, Meditation), 135/174/175 and 137 (healing, spell power of a stat, percent of a stat: applied to item deltas only). Spell modifier ops as the tooltips confirm them: 0 = direct damage/healing only, 22 = periodic only, 3/12/23 = base points of effect 0/1/2, 8 = of every effect, 7 crit, 15 crit damage bonus, 16 hit, 14 cost, 10 cast time, 11 cooldown, 1 duration; percent modifiers multiply. Sheet-visible auras (flat stats, flat bonus damage, spell crit, hit — so also Suppression) are skipped on purpose: the snapshot has them already. What the generic path cannot say sits in `sim/data/overrides.json` with a source note per entry and the rule kinds `life_tap_pct`, `dot_crit`, `channel_dot_haste`, `dot_stack`, `school_damage_pct`, `wand_pct`, `generic`, `ignore`; `effect` names the effect index whose trait value the rule uses, `unverified: true` marks an assumption (Shadowform, Shadow Weaving).
- **Coverage report** (engine 0.3.0, `coverage` in the answer; `run.coverage`): every known spell and every talent with a status — `used`, `sheet` (already in the character sheet's numbers), `idle` (modeled and tried, but not in the best rotation; spells carry the metric of the best rotation with them), `unmodeled` (would matter, the model does not have it: e.g. Power Word: Shield as an absorb, Dark Sacrifice for mana, Drain Soul, Searing Pain, kill and proc talents), `none` (cannot change the metric) — plus a reason code, `unverified` with the rule's note, `candidates` (rotations compared) and `talentValues`. `upgrades.coverage_out` turns the codes into sentences (`COVERAGE_SPELL`, `COVERAGE_TALENT`; an unknown code reads "an effect the model does not know"), the CLI prints them, the upgrades page shows them as the expandable list "What the model does with your spells and talents" with an "assumption" badge (the note on hover). Before reporting engine numbers, read this list: it is the answer to "what did the model leave out".
- **Rotation candidates:** a class module returns every priority list the character can cast (`warlock.Rotations`, `priest.Rotations`), the engine evaluates all and keeps the best. Warlock: Bane of Agony, Corruption and Siphon Life always; Immolate and Death Coil each with and without; one filler of Wrack (Forever's channeled Affliction talent), Shadow Bolt or Drain Life (12 candidates for Malgruk). Priest `dps`: Shadow Word: Pain and Mind Blast always, Holy Fire and Devouring Plague each with and without, Mind Flay or Smite as the filler.
- **Self-healing and Life Tap:** spells that return health (`Leech`: Siphon Life, Drain Life, Death Coil, Devouring Plague) and health per 5 s (gear, plus Demon Armor/Skin through `warlock.ArmorRegen`, taken as always active) refill what Life Tap spends. The health budget for taps is 40 % of the health pool over the fight (`healthUseFraction`) + hp5 + leech; the answer has `selfHealPs`, the breakdown rows `leech` ("returns N health per second").
- **Closed form** (`engine.Evaluate` in `cycle.go`): maintenance spells (DoTs, HoTs, cooldowns) are recast on average half a filler cast late (their cycle is stretched by filler share × filler cast time / 2). When the mana does not last, the maintenance keeps priority: Life Tap takes its time from the filler, missing mana lowers the filler's share, the wand fills the rest; only when the maintenance itself is unaffordable it is scaled down. A channel that makes DoTs tick faster (Wrack, rule `channel_dot_haste`) multiplies their damage and leech by 1 + filler share × haste.
- **Before and after (2026-11-20, 60 s, +2 levels):** Malgruk 124.4 DPS (app 1.9.1: Shadow Bolt filler, no Wrack, no leech, talent values of rank 1) → 273.8 DPS (Wrack 81.6 % of the time, DoTs ticking faster under it). Most of the rise is Wrack, whose mechanic the player confirmed in the game (see below). Siegfried stays at 111.3 HPS.
- **Confirmed in the game by the player (2026-11-20):** Corruption, Bane of Agony and Siphon Life keep their duration while Wrack is channeled, so the doubled tick rate is extra damage; and with Pandemic the DoTs crit. Both rules lost their `unverified` flag. **Still assumptions:** the base crit bonus of 50 % that Pandemic raises (Classic value), Shadowform as always active, Shadow Weaving at five stacks.
- **Spellbook:** the engine prefers an exported spellbook (`WoWMCP_Char.spellbook.spells`, addon 1.11 `collectSpellbook`) and otherwise assumes every trainer rank up to the level plus the talent spells (`spellbookSource: "assumed"`, shown in the summary). Verified in the game on 2026-11-20: Malgruk's 1.11 snapshot carries the book and the engine answers with `spellbookSource: "export"`.
- **Model gaps:** no partial resists, no procs, GCD and cast times not haste-scaled, Life Tap without spell-power scaling, absorbs (Power Word: Shield) and mana returns (Dark Sacrifice) not counted, group heals and Renew ranks not compared, no multi-target spells (Hellfire, Rain of Fire), no execute phase (Drain Soul), no pet, the `dps` metric gives survival stamina no value beyond the Life Tap budget (the old scale's `survival_share` has no counterpart). The coverage report names what this means for a character.
- **Binary lookup** (`simengine.find_binary`): `SIMFOREVER_BIN`, `sim/simforever(.exe)` (local build, gitignored), `../bin` next to the packaged scripts (CI builds it into `app/build/bin`, electron-builder ships it like uv), then the PATH. A path ending in `.py` runs through the Python interpreter — that is the test stub in `test_upgrades.py`.
- **Fight:** `--fight-seconds` (default 60) and `--target-delta` (default: the profile's target, +2 leveling / +3 dungeon) feed the mana budget and the hit table. Hit uses the same `SPELL_MISS`/`MIN_MISS` constants as the scale.
- **Defaults:** `upgrades.compute()` defaults to `engine="off"` (so tests and old callers stay put); the CLI, the bridge and `ingame.py` pass `auto`, so the app and the in-game lists rate with the engine wherever it runs and fall back to the weight scale otherwise — except classes the engine models besides the warlock (the priest): they never fall back to the warlock scale, without a running engine they get an error. The upgrades page has a Rating select (combat model/weight scale), fight length, enemy level and — for classes with several metrics — a Metric select; `ingame.py` texts name the unit (DPS or HPS) when the engine answered.
- **Priest (M3):** metrics `hps` (sustained healing under the mana budget over the fight), `ttoom` (how long the mana lasts at full healing; capped at 3600 s so sustainable states compare) and `dps` (see "Rotation candidates"). The healer rotation is Renew plus one single-target heal; the engine tries **every known rank** of Lesser Heal/Heal/Greater Heal/Flash Heal and keeps the best sustained healing — that is how downranking is modeled while the Forever downrank penalty is unmeasured. When the winner is not what a player casts by default, the answer carries `downrank` = {spell, rank, instead, gainPct} — the comparison prefers the next higher known rank of the **same** chain ("Heal rank 1 instead of rank 2") and falls back to the biggest other heal: the app shows "Downranking pays: heal with … instead of …", the in-game note appends "heal with …", and the breakdown labels every spell with its rank line (the game's own text from the spellbook export, else the chain position). The answer also carries `healOptions`: every heal-rank candidate with healing per cast, mana, cast time, **healing per mana** and the sustained HPS the choice uses, sorted by the latter — the app renders them as the expandable "Heal ranks" table, the CLI prints them under the summary. Spirit regeneration: Classic approximation per class (priest 13 + spirit/4 per 2 s tick, warlock 8 + spirit/4; `regen` in run.go), of which only the Meditation share works while casting. The default metric follows the spec, which `simengine.spec_of` reads from where the talent points sit (tree order as the client tabs: Discipline/Holy/Shadow); Shadow defaults to `dps`, everything else `hps`. Meditation and Spiritual Guidance are decoded from their auras (Spiritual Guidance applies to spirit deltas only, the sheet has the base); Shadowform, Shadow Weaving and Wand Specialization are overrides.
- **Engine item stats:** in engine mode the deltas come from `simengine.norm_item` (not `norm_stats`): it keeps healing, per-school damage and the difference between "damage done" and "damage and healing done" (`spDamage` vs `sp`), so healer items are rated correctly. The weight scale keeps its own narrower `norm_stats`.
- **Monte-Carlo (M5, since engine 0.2.0; the engine is at 0.3.0):** `--method montecarlo` (UI: Rating "Kampfmodell (Monte-Carlo)") plays the rotation in `sim/engine/mc.go`: real hit/crit/damage rolls per cast, DoTs tick on their schedule and are recast when they fall off, Life Tap on demand, wand when mana runs dry, full spirit regeneration five seconds after the last cast. The baseline carries `mc = {iterations (default 10000), mean, stdDev, p10, p90}` and its value becomes the MC mean; only the `mcTop` (16) biggest closed-form gains are replayed (`results[key].mc = true`), the rest keep the deterministic delta. All runs share the per-iteration seed (common random numbers), so gear differences are not dice differences, and the same seed reproduces the same numbers. DoT ticks apply their crit as an expectation per tick, not as a roll. Health is tracked: Life Tap may take it down to 60 % of the pool, leech and hp5 refill it; the player taps early (health bar full, mana will not last for the rest of the fight) so that no leech is wasted, and a filler that returns health goes before the DoTs when health blocks tapping. Agreement with the closed form for Malgruk: 60 s 271.5 vs 273.8, 180 s 244.4 vs 252.8, 600 s 168.2 vs 176.6 (Monte-Carlo first; the rest is the fight start, where the DoTs go up one after another, and ticks cut off at the end). The in-game lists always use the fast expectation method.

## Writs and trade crates (`scripts/writs.py`)

- **Gold on completion:** The writ quest (item → `ItemSparse.StartQuestID`, e.g. 264012 → 94212) pays no gold itself. The game's quest cache (`_forever_\Cache\WDB\<locale>\questcache.wdb`, record = quest ID, size, data; `RewardMoney` at offset 48, reputation from offset 300 as faction and value × 100) has 0 gold and 75/125/200 reputation with the factions 2586 and 2587. The pay is a coin pouch (according to wow.gg; the DB2 has four, 284583–284586) whose content is rolled when it is opened. Until the addon (since 1.5) has measured pouches, estimates per tier apply (`POUCH_ESTIMATE`: Journeyman 33 s, Expert 70 s, Artisan 75 s, after conquestcapped.com, Nov 2026). Measured, the pouch of the own quest counts, otherwise the pouch other writs of the same tier gave. Net = writ + item − pouch, sorted by net per reputation; negative = profit.
- **Trade crates:** A waylaid (empty) crate (248682–248699 and 248702–248713: herbs, ore, textiles, curiosities, fabrics, ingots, parts; Expert and Artisan with earthly and flowering herbs) is filled with exactly one bundle. The spell "Fill Crate" has the amounts as dummy effects in `SpellEffect`; `CRATES` is checked against that, the item IDs of the bundles are only in the guides. The sealed crate (common 248765–248769, uncommon 248770–248774, rare 248775–248779, each Apprentice, Journeyman, Expert, Artisan, Elite) gives Merchant's Favor (currency 3402) at the trade representative, no gold and no reputation. Favor common/uncommon according to urgametips.com and wow.gg: Apprentice 5/10, Journeyman 10/20, Expert 15/30; Artisan 20/40 is extrapolated. Values measured by the addon win. Character level: Apprentice and Journeyman 10, Expert 20, Artisan 35.
- **Calculation:** the empty crate at the AH price (owned 0, without an AH price "incomplete") + the cheapest bundle the AH has in the full amount (own bundles 0). "Per favor" uses the common crate.
- **Unknown:** what the quality of the sealed crate depends on, Elite crates (no waylaid Elite crate in the DB2, content unknown) and what a Merchant's Favor is worth in gold (favor vendor: recipes 15–360, tabard 200, pack kodo 6000).
- The writ list in `writs.py` is from wow.gg (Nov 2026); add new writs there to `WRITS` and their names in both languages to `scripts/data/item_names.json`.

## Recipe calculation (`scripts/recipes.py`)

- **Catalog** from the DB2 tables (`build_catalog`, stored as `scripts/cache/recipes-<build>-<locale>.json`; raise `CATALOG_VERSION` when the structure changes): `SkillLineAbility` (recipes per skill line; `TrivialSkillLineRankLow` = yellow, `…High` = grey, green from the middle; `MinSkillLineRank` is always 1 in Forever and is useless as the required skill), `SpellReagents`, `SpellEffect` (effect 24 = created item, amount in `EffectBasePointsF`; effect 36 = learn a recipe), `ItemEffect` + `ItemXItemEffect` (recipe items: through a learn effect or, as in Classic, with the recipe spell directly on the item), `ItemSparse` (names, `BuyPrice`/`VendorStackCount`, `SellPrice`, `Bonding`, `RequiredSkillRank` = required skill of the recipe item), `SpellCooldowns` (transmutes; in Forever e.g. Iron to Gold 1 h, Arcanite 47 h). Gathering professions (182, 186, 393, 356) are left out. If the tables cannot be downloaded, `compute` reports that instead of an empty result.
- **Table download** (`icons.table`): a file counts as a table if its first line has an `ID` column (`SkillLineAbility` does not start with it) and is written in one step, because several bridge processes may fetch the same table at once.
- **Learned** comes only from the addon export (`WoWMCP_Char.recipes`). The profession window API delivers data in Forever only while the window is open. Forever's interface hides unlearned recipes (`Camelot/Blizzard_Professions.lua`), so the DB2 is the catalog. Reagents and amount from the game win over the DB2.
- **Profit** = lowest AH price × amount × 0.95 − reagents. Reagents at the cheaper price from AH and vendor: first vendor prices seen in the game (unlimited ones only), otherwise `VENDOR_ITEMS` (vials, spices, threads, dyes, flux …) with `BuyPrice / VendorStackCount`. Own reagents count at the market price. Bound results and results without an AH price count at the vendor sell price. Notes appear when the price is older than the last scan, the lowest price is below 60 % of the median of the last 7 scan days or a reagent has no price.
- **Profit history** (`profit_history`, `trend_of`; fields `history` and `trend` per recipe): the same profit on the last 8 full scan days. A day counts as a full scan if it has at least 30 % of the entries of the biggest scan day (Auctionator also writes day prices for single searches). Auctionator stores per day only the highest (`h`) and lowest (`l`) minimum price; the day price is the middle, on the last scan day the current minimum price, so that the last point equals the profit shown. Days without a price for the result or a reagent are missing. Trend = change over the last three scan days, below 20 % counts as stable. For "falling", the note "profit is falling (on … still …)" replaces the note "cheap right now". Background: in the first weeks after launch the profit of freely craftable potions fell to about zero within 3 to 5 days as soon as many had the recipe; only what a cooldown limits stayed stable (transmute Arcanite). Auctionator does not know sales volumes.
- **Missing recipes:** The source is a recipe item in the AH (price, offers), a recipe seen at a vendor, a recipe item "not in the AH" (drop, reputation or vendor, unknown) or the trainer (no recipe item, `AcquireMethod` ≠ 3; `AcquireMethod` 3 without a recipe item counts as not obtainable). Learnable: recipe item with `RequiredSkillRank` ≤ skill; at the trainer certain if "yellow" ≤ skill (the required skill is never above yellow), otherwise unknown. "Pays more" = more profit than the best learned recipe with at least 3 offers. Sorted first by "learnable now", then by profit.
- **Not considered:** multi-step crafting (intermediates count at the AH price), trainer costs (not in the DB2), AH deposit, faction restrictions of recipes. The app knows vendor prices for recipes only once the addon has seen the vendor.

## Consumables (`scripts/consumables.py`)

- **Catalog** from the DB2 tables (`build_catalog`, stored as `scripts/cache/consumables-<build>-<locale>.json`; raise `CATALOG_VERSION` when the structure changes): every item of `Item.ClassID` 0 with its spell (`ItemEffect` + `ItemXItemEffect`), decoded from `SpellEffect` (`decode`): effect 10 = heal, 30 with misc 0 = mana (range = base points × (1 ± `Variance`/2), e.g. Healing Potion 320 → 280–360), aura 84/85 in food (subclass 5) = health/mana per 5 s for the duration (`SpellMisc.DurationIndex` → `SpellDuration`), aura 8 in bandages = heal per period, effect 54 = temporary weapon enchantment (`SpellItemEnchantment`: type 3 = equip spell, decoded again; type 5 = stat), other auras through `AURA` (13 spell damage by school mask, 29 attributes, 34 health, 85 mp5, 57 spell crit, 290 crit, 674/22 armor, …). Skipped: conjured items (`Flags_0` & 2) and names with "Deprecated", "Test" and similar.
- **Forever's buff food:** "Nutritious Food" triggers the eating spell (effect 64) and, after 10 s, Well Fed through aura 227; the amount is on the outer effect (`$s2`, e.g. Nightfin Soup +22 spell damage), the Well Fed aura itself holds 1. Some Well Fed spells also mention an XP bonus (spell 1243969, depends on a player condition); it is not shown.
- **Usable:** `RequiredLevel` ≤ level, `AllowableClass` contains the class, required skill reached (bandages ask for skill line 2942, which counts as First Aid 129).
- **Listed** are items the character can get at all: in bags or bank, in the AH, at a vendor (seen by the addon, or `VENDOR_FOOD`: bread, meat, fish, cheese, fruit, mushrooms and water every innkeeper sells, at `BuyPrice / VendorStackCount`) or made by a profession (recipe catalog of `recipes.py`). "Best now" = the strongest one available now (owned, sold or with a learned recipe). Items with the same effect are merged into one row ("same effect") unless they are owned or craftable by the character. "Next" = the stronger item with the lowest required level (or skill) above the character.
- **Relevant stats** per class in `RELEVANT` (casters: spell power, intellect, spirit, mp5, stamina, spell crit, warlock also shadow and fire; melee: strength, agility, attack power, crit, armor; Paladin, Shaman, Druid everything).
- **Not considered:** whether elixirs stack (battle/guardian rules are unknown for Forever), potion cooldowns, resistance and protection potions, utility (speed, water breathing), rogue poisons, sharpening stones without a stat.
